# 8. Выявление и устранение «горячих» шардов

## Набор метрик состояния шардов

- Получение форматированного отчета о распределении данных и блоков (chunks) по шардам в кластере, показывая размер данных и их процентное соотношение на каждом шарде, а также общее количество документов
```
db.collection.getShardDistribution()
```

- Форматированный отчет о конфигурации шардинга, распределении чанков (chunk) по шардам и активных экземплярах mongos, (true) в детальном виде
```
db.printShardingStatus(true)
```

- Определение часто используемых категорий товаров
```
db.collection.aggregate([{$group:{id:"$category", count:{$sum:1}}}])
```

- Получение детальной информации о состоянии и производительности сервера,
  возвращая документ с метриками работы, такие как активность, соединения, кэширование, репликация
```
db.serverStatus()
```
Возвращает:
- connections: Информация о текущих и максимальных подключениях, ожидающих запросах.
- opcounters: Статистика операций (insert, query, update, delete).
- mem: Использование памяти (Resident, Virtual,mapped).
- network: Статистика сетевых операций.
- locks: Состояние блокировок.
- repl: Статус репликации (если это реплика).
- storageEngine: Информация о движке хранения.

## Механизмы автоматического перераспределения данных

- Применение встроенного балансировщика
```
sh.setBalancerState(state); //включение балансировщика
sh.setBalancerState(true, { start: "22:00", stop: "06:00" }); // включить балансировщик с окном с 22:00 до 06:00

# проверки состояния балансировщика шардинга
sh.getBalancerState(); // Возвращает, включен ли балансировщик
sh.isBalancerRunning(); // Возвращает, работает ли балансировщик в данный момент
```

- Настроить диапазонное шардирование, например по категориям и ценам
```
sh.addShardTag("shard1", "electronics_range_price1");
sh.addShardTag("shard2", "electronics_range_price2");

sh.addTagRange(
  "somedb.product",
  { category: "Электроника", price: 0 },
  { category: "Электроника", price: 1000 },
  "electronics_range_price1"
);
sh.addTagRange(
  "somedb.product",
  { category: "Электроника", price: 1000 },
  { category: "Электроника", price: 2000 },
  "electronics_range_price2"
);
```

- Использование составного ключа шардирования, например по product_id и category
```
db.getSiblingDB("<имя_БД>").<имя_коллекции>.createIndex( { "<ключ_шардирования>": <1_или_-1> } ); //Создаем индекс на поле, которое будет использоваться как ключ шардирования 
sh.shardCollection("<имя_БД>.<коллекция>", { "<ключ_шардирования>": <1_или_-1> }); //Шардирование коллекции
sh.shardCollection("<имя_БД>.<коллекция>", { "<ключ_шардирования>": <1_или_-1>, "<ключ_шардирования>": <1_или_-1> }); //Шардирование коллекции с состаным ключем
```

# 10. Миграция на Cassandra: модель данных, стратегии репликации и шардирования

## 10.1 Какие части данных интернет-магазина являются критически важными с точки зрения целостности и скорости обработки.

- товары - Частые обновления остатков при покупках.
- заказы - Быстрое создание заказов с одновременным списанием остатков.
- история заказов - Отображение статуса заказа.
- корзины - информация обновляяется в реальном времени

Для этих данных применение Cassandra имеет смысл, так как она как раз относится к AP по CAP-теореме (доступность и устойчивость к разделению).

## 10.2 Концептуальная модель для выбранных критически важных сущностей.

1. Заказы (orders)
   [orders.plantuml](orders.plantuml)
    - Partition key: id - уникальный id, равномерное распределение без горячих партиций
    - Кластерный ключ: date, user_id - порядок по дате оформления заказа

2. Товары (products)
   [products.plantuml](products.plantuml)
    - Partition key: id, category - уникальный id, равномерное распределение без горячих партиций
    - Кластерный ключ - Не требуется специальный. Внутри партиции (все товары одной категории) данные хранятся в порядке их записи..

3. Корзины (carts)
   [carts.plantuml](carts.plantuml)
    - Partition key: user_id, session_id - уникальные идентификаторы, равномерное распределение без горячих партиций
    - Кластерный ключ: updated_at - обеспечивает порядок по времени обновления

## 10.3 Стратегии обеспечения целостности

| Стратегия           | Сущности                  | Обоснование                                                                                             |
|---------------------|---------------------------|---------------------------------------------------------------------------------------------------------|
| Hinted Handoff      | продукты, истории заказов | Учитываем, что данные могут расходится в какой-то момент времени                                        |
| Read Repair         | корзина                   | Корзина должна быть максимальна актуальной, поэтому восстанавливаем (если необходимо) при чтении данные |
| Anti-Entropy Repair | продукты, заказы          | Периодически необходимо делать синхронизацию, но так как объем большой делаем в фоновое время           |
